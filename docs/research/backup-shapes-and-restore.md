# Backup shapes and restore mechanics: what other systems do

This file collects evidence for the design conversation on [issue #36](https://github.com/assetcorp/sirannon-db/issues/36). Its sibling, `backup-interoperability.md`, establishes the mechanics of producing backup bytes and reporting on them, so this one takes up three product questions instead: what a backup becomes once it stops being one full copy per cycle, how the pieces come back together when they are in object storage rather than on local disk, and where an established system takes its backups in a replicated deployment. Every claim names the document or the source file it came from, and I opened each of them. This file recommends nothing and proposes no design for Sirannon.

## 1. What a backup run produces, and what has to happen before the data can be served

### PostgreSQL

A full run of `pg_basebackup` produces either a copy of the data directory or a set of tar files, plus a backup manifest. An incremental run produces the same shape with most relation files replaced by smaller ones. The [pg_basebackup reference](https://www.postgresql.org/docs/current/app-pgbasebackup.html) states what that costs the operator: "An incremental backup cannot be used directly; instead, pg_combinebackup must first be used to combine it with the previous backups upon which it depends."

The chain is the operator's responsibility. The [continuous archiving documentation](https://www.postgresql.org/docs/current/continuous-archiving.html) states that "When restoring an incremental backup, it will be necessary to have not only the incremental backup itself but also all earlier backups that are required to supply the blocks omitted from the incremental backup", and it goes further: "PostgreSQL has no built-in mechanism to figure out which backups are still needed as a basis for restoring later incremental backups. You must keep track of the relationships between your full and incremental backups on your own, and be certain not to remove earlier backups if they might be needed when restoring later incremental backups."

PostgreSQL ships the recombination tool in core, and the operator runs it by hand as one step of a documented procedure. Step 5 of the recovery procedure states: "If you're restoring an incremental backup, you'll need to restore the incremental backup and all earlier backups upon which it directly or indirectly depends to the machine where you are performing the restore. These backups will need to be placed in separate directories, not the target directories where you want the running server to end up. Once this is done, use pg_combinebackup to pull data from the full backup and all of the subsequent incremental backups and write out a synthetic full backup to the target directories."

The output is itself a full backup, which bounds how long a chain can grow. The [pg_combinebackup reference](https://www.postgresql.org/docs/current/app-pgcombinebackup.html) states that "Since the output of pg_combinebackup is a synthetic full backup, it can be used as an input to a future invocation of pg_combinebackup." The same page draws a line around what the tool checks: "pg_combinebackup only attempts to verify that the backups have the correct relationship to each other, not that each individual backup is intact; for that, use pg_verifybackup."

Even after recombination, no artefact is a running database. The operator must still supply the WAL, write a recovery configuration, create `recovery.signal`, and start the server, which then replays. PostgreSQL's other backup route avoids all of this at the cost of the physical format, because [pg_dump](https://www.postgresql.org/docs/current/backup-dump.html) produces "a file with SQL commands that, when fed back to the server, will recreate the database in the same state as it was at the time of the dump", restored with `psql` or `pg_restore`.

### MySQL

MySQL Community ships no hot physical backup tool. The [backup methods page](https://dev.mysql.com/doc/refman/8.4/en/backup-methods.html) states that "Customers of MySQL Enterprise Edition can use the MySQL Enterprise Backup product to do physical backups of entire instances or selected databases, tables, or both. This product includes features for incremental and compressed backups." The community answer is `mysqldump`, which is logical and single-file, plus the binary logs. The [point-in-time recovery page](https://dev.mysql.com/doc/refman/8.4/en/point-in-time-recovery-binlog.html) states that "The source of information for point-in-time recovery is the set of binary log files generated subsequent to the full backup operation", and the operator restores the full backup first and then pipes `mysqlbinlog` output into a client.

Percona XtraBackup fills that gap for MySQL Community, and it makes the post-processing step explicit and mandatory. Its [restore page](https://docs.percona.com/percona-xtrabackup/8.4/restore-a-backup.html) states the requirement as a warning: "Backup needs to be prepared before it can be restored." An incremental run produces `.delta` files plus an `xtrabackup_checkpoints` file, and the [prepare page for incremental backups](https://docs.percona.com/percona-xtrabackup/8.4/prepare-incremental-backup.html) states that the operator applies each increment into the base directory in order, with `--apply-log-only` on every step but the last, because "If you do not use the `--apply-log-only` option to prevent the rollback phase, then your incremental backups are unusable." The merge happens in place: "The final data is in `/data/backups/base`, not in the incremental directory."

MySQL Enterprise Backup takes the same shape from the vendor. Its [incremental backup page](https://dev.mysql.com/doc/mysql-enterprise-backup/8.4/en/mysqlbackup.incremental.html) states that "Incremental backups detect changes at the level of pages in the InnoDB data files, as opposed to table rows; each page that has changed is backed up", and that "to restore data up to, for example, time `t`, you start with restoring the full backup, and then restore the incremental backups one by one, until you are finished with the incremental backup taken for time t."

### MongoDB

MongoDB's own manual offers four routes, per the [backup methods page](https://www.mongodb.com/docs/manual/core/backups/): Cloud Manager or Ops Manager, filesystem snapshots, copying the data files with `cp` or `rsync`, and `mongodump` with `mongorestore`. Only the managed route offers continuous point-in-time backup and restore.

`mongodump` produces a directory of BSON files with a metadata JSON file per collection, plus an `oplog.bson` file when the operator passes `--oplog`, per the [mongodump reference](https://www.mongodb.com/docs/database-tools/mongodump/). The same page documents `--archive`, which turns the whole dump into a single binary file or writes it to standard output. Nothing else has to happen before `mongorestore` can load it, so the artefact is self-contained in the sense the issue asks about, and the manual bounds the route by deployment size: `mongodump` and `mongorestore` "are tools for backing up and restoring small MongoDB deployments."

Ops Manager produces snapshots plus oplog data, and the artefacts are not files the operator handles. The [backup process page](https://www.mongodb.com/docs/ops-manager/current/core/backup-overview/) states that "The backup process takes a snapshot of the data directory at its scheduled snapshot intervals", that the agent "opens a $backupCursor at the storage engine level to allow copying of database files in a consistent state while still accepting writes", and that "Oplog tailing of the primary node is required for backups."

Percona Backup for MongoDB offers incremental physical backups, and it constrains the chain in an unusual way. Its [incremental backup page](https://docs.percona.com/percona-backup-mongodb/features/incremental-backup.html) states that "During incremental backups, Percona Backup for MongoDB saves only the data that was changed after the previous backup was taken", and then that "Percona Backup for MongoDB tracks the backup history only on the node where the base incremental backup was taken. This means that subsequent incremental backups must always be run on that very node." Losing that node ends the chain: "If the node with the base incremental backup is down or unavailable, you must start the incremental backup chain anew on another node."

### SQL Server

SQL Server is the one system in this set where the database engine performs the recombination, so no separate tool exists and the operator never runs one. The [restore and recovery overview](https://learn.microsoft.com/en-us/sql/relational-databases/backup-restore/restore-and-recovery-overview-sql-server) states that "To perform a database restore, the Database Engine executes three steps: Creates the database and transaction log files if they don't already exist. Copies all the data, log, and index pages from the backup media of a database to the database files. Applies the transaction log, in what is known as the recovery process."

The artefacts are a full backup, optional differentials, and log backups. The same page defines the sequence: "A complete database restore involves restoring a full database backup and, optionally, a differential backup (if any), followed by restoring all subsequent log backups (in sequence). The complete database restore is finished by recovering the last log backup and also restoring it (RESTORE WITH RECOVERY)." A full backup is restorable on its own, and the others are not. The [differential backup page](https://learn.microsoft.com/en-us/sql/relational-databases/backup-restore/differential-backups-sql-server) states that "before you restore a differential backup, you must restore its base", and it also names the failure mode that keeps a differential chain short: "The longer the time between a differential backup and its base, the larger the differential backup is likely to be. This means that the differential backups can eventually approach the differential base in size."

SQL Server also offers a shape that changes the arithmetic entirely, when the database files themselves are in Azure Blob Storage. The [file-snapshot backup page](https://learn.microsoft.com/en-us/sql/relational-databases/backup-restore/file-snapshot-backups-for-database-files-in-azure) states that "A file-snapshot backup is a set of Azure snapshots of the blobs that contain the database files, plus a backup file with pointers to those file-snapshots", and that "After the initial full backup that establishes the transaction log backup chain (which can itself be a file-snapshot backup), you need only transaction log backups." A restore then needs at most two backup sets: "Each file-snapshot backup set contains a file-snapshot of every database file, so a restore needs at most two adjacent file-snapshot backup sets."

### SQLite, and the opposite extreme

Litestream is the SQLite-focused product that answers this question in full. A replication run produces LTX files and periodic snapshots, per the [how-it-works page](https://litestream.io/how-it-works/): "New WAL pages are packaged into LTX files (Litestream Transaction Log files)". Litestream organises those files into four levels, where L0 holds "uncompacted per-sync batches written continuously during replication", L1, L2, and L3 hold "compacted files, merged every 30 seconds, 5 minutes, and 1 hour by default", and the snapshot level holds "a full copy of the database, created every 24 hours by default". No single LTX file is usable on its own, because "To restore a database, Litestream fetches the most recent snapshot that does not overshoot the requested restore point and then applies each subsequent LTX file in TXID order to bring the database up to that point."

Litestream ships the recombination as one command, and it produces an ordinary SQLite file. Restore granularity is a documented consequence of the file layout: "Litestream replays whole LTX files and never applies part of one, so your restore points are the boundaries of the files that still exist in the replica."

Cloudflare D1 takes the shape away from the user completely. Its [Time Travel documentation](https://developers.cloudflare.com/d1/reference/time-travel/) describes it as "D1's approach to backups and point-in-time-recovery", which "allows you to restore a database to any minute within the last 30 days", and states that "Time Travel automatically creates bookmarks on your behalf. You do not need to manually trigger or remember to initiate a backup." There is no artefact, no chain, and no recombination step the user performs, because restoring "is a destructive operation, and overwrites the database in place."

### The pattern across the five

Every vendor that stopped copying the whole database gave up the property that one artefact is usable on its own. They then split on who performs the extra step. PostgreSQL and Percona require the operator to run a separate command at a separate moment, whereas SQL Server folds the step into the engine's own `RESTORE`, Litestream folds it into `restore`, and Cloudflare hides it entirely. In every case except pg_dump, mongodump, and D1, a log replay still follows before the data can be served.

## 2. Restoring when the pieces are in object storage

### PostgreSQL's own tooling stops at the local filesystem

`pg_combinebackup` cannot access anything but a local filesystem. The [reference page](https://www.postgresql.org/docs/current/app-pgcombinebackup.html) gives its synopsis as `pg_combinebackup [option...] [backup_directory...]`, with output to a directory named by `-o`, and it documents no storage option of any kind. Its source confirms this at the level of the system calls. In [pg_combinebackup.c](https://github.com/postgres/postgres/blob/REL_18_STABLE/src/bin/pg_combinebackup/pg_combinebackup.c) the program takes the directories straight from `argv`, walks them with `opendir()` and `readdir()`, opens files with `open()`, sizes them with `stat()`, and copies with `copy_file_range()` or `copyfile()`. There is no network code, no object-storage client, and no tar reader anywhere in the 1,419-line file, so a tar-format backup would have to be unpacked first and an object-storage backup downloaded first.

PostgreSQL documents the disk cost only by implication. The recovery procedure requires the full backup and every incremental "placed in separate directories, not the target directories", and then the synthetic full backup written into the target directories, so free space of roughly the database size plus the whole chain would be needed for a plain run. PostgreSQL's answer to that is not remote access but block sharing: `--clone` uses "efficient file cloning (also known as 'reflinks' on some systems) instead of copying files to the new data directory", `--copy-file-range` uses the `copy_file_range` system call, and `-k/--link` uses hard links, which "use less disk space" but "requires that the input backups and the output directory are in the same file system" and carries a warning that later modifications to either directory affect the other.

### pgBackRest restores from the repository straight into the data directory

pgBackRest is the counter-example within the same ecosystem. Its repository can be object storage: the [option reference](https://github.com/pgbackrest/pgbackrest/blob/main/doc/xml/reference.xml) lists `repo-type` values of `azure`, `cifs`, `gcs`, `posix`, `s3`, and `sftp`. Its restore command takes a backup set and writes into the cluster directory, and the `delta` option states the default expectation plainly: "During a restore, by default the PostgreSQL data and tablespace directories are expected to be present but empty. This option performs a delta restore using checksums." Nothing in the command reference describes a staging directory, and the operator names no scratch space anywhere.

The block incremental feature makes the remote access explicit. The same reference states that block incremental "saves space in the repository and can improve delta restore performance because individual blocks can be fetched without reading the entire file from the repository", which would require ranged requests against the repository rather than whole-object downloads.

### WAL-G composes the chain during the fetch

WAL-G takes the backup name and a destination directory. Its [PostgreSQL documentation](https://raw.githubusercontent.com/wal-g/wal-g/master/docs/PostgreSQL.md) states that "When fetching base backups, the user should pass in the name of the backup and a path to a directory to extract to. If this directory does not exist, WAL-G will create it and any intermediate subdirectories." For a chain of delta backups there is no separate combine step at all: "Restoration process will automatically fetch all necessary deltas and base backup and compose valid restored backup (you still need WALs after start of last backup to restore consistent cluster)."

Two flags exist purely to cut the work that composition costs. `--reverse-unpack` lets WAL-G "unpack delta backups in reverse order to improve fetch efficiency", and `--skip-redundant-tars`, which requires it, skips archives whose contents a later delta would overwrite anyway. The documentation states the destination and the ordering, and it does not state whether the downloaded tarballs are held on disk before extraction, so I have marked that below as unestablished.

### Percona's cloud path is asymmetric

The upload direction needs no local disk. The [xbcloud overview](https://docs.percona.com/percona-xtrabackup/8.4/xbcloud-binary-overview.html) states that xbcloud "enables you to stream backups directly to cloud storage without requiring local disk space, making it ideal for large database environments", and that it "accepts input via pipes from xbstream". Objects are chunked, with "The default chunk size is 10MB, which you can adjust using `--read-buffer-size`."

The download direction goes through local disk. The [S3 page](https://docs.percona.com/percona-xtrabackup/8.4/xbcloud-s3.html) gives the restore command as `xbcloud get s3://operator-testing/bak22 --s3-endpoint=... --parallel=10 2>download.log | xbstream -x -C restore --parallel=8`, so the stream is extracted into a local directory. `--prepare` then runs against that directory, and only then can the operator move the result into place. The [restore page](https://docs.percona.com/percona-xtrabackup/8.4/restore-a-backup.html) describes the two ways to do that: `--copy-back` "Copies backup files from the backup directory to the datadir. Preserves the original backup", while `--move-back` "Moves backup files to the datadir. Removes files from the backup directory." The same page requires that "The datadir must be empty before restoring the backup." So `--copy-back` needs free space for the backup and the data directory at once, and `--move-back` exists to avoid that, at the price of destroying the backup copy as it goes.

### SQL Server restores from a URL with no download step

SQL Server's `RESTORE` accepts a URL as its source device, and the engine performs the transfer. The [backup to URL page](https://learn.microsoft.com/en-us/sql/relational-databases/backup-restore/sql-server-backup-to-url) lists `FROM (URL)` as supported, with the note that "The `FROM URL` argument is used to specify the URL path for the backup file", and it gives a worked point-in-time example that restores a database and then a log directly from two blob URLs. `RESTORE FILELISTONLY`, `HEADERONLY`, `LABELONLY`, and `VERIFYONLY` are all supported against the same URLs, which would require partial requests against remote backup media rather than whole-file downloads. SQL Server 2022 extended the same syntax to S3-compatible storage.

Azure imposes size limits on that path instead of space limits. "The maximum backup size supported using block blobs is limited to approximately 195.3 GB (50,000 blocks *4 MB MAXTRANSFERSIZE). Block blobs support striping to support substantially larger backup sizes - the limit is a maximum of 64 URLs, which results in the following formula: 64 stripes* 50,000 blocks * 4MB maxtransfersize = 12.8 TB."

### Litestream restores from the replica, and its VFS never downloads the database at all

`litestream restore` takes either a database path from the configuration file or a replica URL directly, per the [restore reference](https://litestream.io/reference/restore/): "This command will restore from a replica without using the Litestream configuration file. It is useful if you don't have a configuration file such as on a development machine." Its `-parallelism` argument "Determines the number of WAL files downloaded in parallel", defaulting to 8, so the tool pulls the pieces from object storage and writes the output database as it goes. The only local requirement the page names is that the output path be free: "Restoration will only run if the output database file does not exist so you cannot accidentally overwrite your running database."

Litestream's VFS extension answers this question from the other side, because it serves queries against a database it never downloads. The [VFS reference](https://litestream.io/reference/vfs/) states that it "provides read-only access to a replicated SQLite database directly from object storage. It registers a VFS named litestream, fetches pages on-demand, and continuously polls the replica for new LTX files." Its performance section states the working set: "On-demand page fetch with LRU caching sized by CacheSize (default 10MB)", with a polling interval of one second by default and up to six retries per page fetch. It "builds an in-memory page index from LTX files, and serves pages directly from remote storage."

MongoDB offers the same idea at the deployment level. The [queryable backup tutorial](https://www.mongodb.com/docs/ops-manager/current/tutorial/query-backup/) states that "Ops Manager provisions these queryable snapshots as read-only MongoDB instances. Specifically, Ops Manager spins up a mongod with data from the selected snapshot store", available "for up to 24 hours" by default. The uses it names are "Restore a subset of data within the MongoDB deployment", comparing versions, and identifying the right point in time. Queries needing disk, such as aggregations with `allowDiskUse`, are refused.

### What the free-disk requirement comes to

No documentation I opened states a disk figure for a restore. The requirement follows from the documented procedures, so the arithmetic below is mine and the individual steps are the vendors'.

A pgBackRest restore, a WAL-G `backup-fetch`, a SQL Server `RESTORE FROM URL`, and a `litestream restore` each write the database once into its destination, and none of them documents a staging area, so each needs free space of about one database. A PostgreSQL incremental restore through `pg_combinebackup` needs the full backup, every incremental, and the synthetic output at once, which is more than two databases unless the operator uses reflinks or hard links. A Percona restore from object storage needs the extracted backup plus the data directory, which is two, and `--move-back` exists to bring that down to roughly one.

Only two products in this set serve data without room for the whole database, and both do so read-only and outside the restore path: Litestream's VFS, and Ops Manager's queryable snapshots. SQL Server's file-snapshot backups produce the same outcome by a third route, because the database files are already blobs and the restore manipulates snapshots of them instead of copying pages.

## 3. Where a backup is taken in a replicated deployment

### PostgreSQL

PostgreSQL supports backups on a standby and documents four costs. The [pg_basebackup reference](https://www.postgresql.org/docs/current/app-pgbasebackup.html) lists them: "The backup history file is not created in the database cluster backed up"; "pg_basebackup cannot force the standby to switch to a new WAL file at the end of backup", so with `-X none` and low write activity on the primary it "may need to wait a long time for the last WAL file required for the backup to be switched and archived"; "If the standby is promoted to be primary during backup, the backup fails"; and "All WAL records required for the backup must contain sufficient full-page writes, which requires you to enable `full_page_writes` on the primary."

Incremental backups add a fifth. The [continuous archiving documentation](https://www.postgresql.org/docs/current/continuous-archiving.html) states that "An incremental backup is only possible if replay would begin from a later checkpoint than for the previous backup upon which it depends. If you take the incremental backup on the primary, this condition is always satisfied, because each backup triggers a new checkpoint. On a standby, replay begins from the most recent restartpoint. Therefore, an incremental backup of a standby server can fail if there has been very little activity since the previous backup, since no new restartpoint might have been created."

Archiving from a standby needs its own setting, and PostgreSQL reserves its strongest warning for an archive shared between two servers. Section 26.2.9 of the [high availability documentation](https://www.postgresql.org/docs/current/warm-standby.html) states that "When the standby has its own WAL archive, set `archive_mode` to `always`, and the standby will call the archive command for every WAL segment it receives", and that a shared archive "requires more care in the `archive_command` or `archive_library`, as it must be careful to not overwrite an existing file with different contents, but return success if the exactly same file is archived twice. And all that must be done free of race conditions, if two servers attempt to archive the same file at the same time." With `archive_mode = on`, a promoted standby "will start archiving after the promotion, but will not archive any WAL or timeline history files that it did not generate itself."

The WAL summariser that incremental backups depend on can run on either side. The [WAL configuration documentation](https://www.postgresql.org/docs/current/runtime-config-wal.html) states that "WAL summarization can be enabled either on a primary or on a standby", with `wal_summary_keep_time` defaulting to 10 days and the warning that "WAL summaries must be available for the entire range of WAL records between the preceding backup and the new one being taken; if not, the incremental backup will fail."

### pgBackRest and WAL-G

pgBackRest makes standby backup an option with three values, per its [option reference](https://github.com/pgbackrest/pgbackrest/blob/main/doc/xml/reference.xml): `y` means "Standby is required for backup", `prefer` means "Backup from standby if available otherwise backup from primary", and `n` means "Backup from primary only". The stated purpose is load: "Enable backup from standby to reduce load on the primary cluster."

What that backup guarantees is stated as an equivalence, and the mechanism behind it is stated too. The [user guide](https://github.com/pgbackrest/pgbackrest/blob/main/doc/xml/user-guide.xml) states that "pgBackRest creates a standby backup that is identical to a backup performed on the primary. It does this by starting/stopping the backup on the pg1 host, copying only files that are replicated from the pg2 host, then copying the remaining few files from the pg1 host. This means that logs and statistics from the primary database will be included in the backup." Both hosts must therefore be reachable: "Both the primary and standby databases are required to perform the backup, though the vast majority of the files will be copied from the standby to reduce load on the primary." pgBackRest works out the roles itself, since "pgBackRest will automatically determine which is the primary and which is the standby", and "If more than one standby is configured then the first running standby found will be used for the backup."

WAL-G supports a standby backup and treats promotion during one as a failure. Its [documentation](https://raw.githubusercontent.com/wal-g/wal-g/master/docs/PostgreSQL.md) states that "If a backup is started from a standby server, WAL-G will monitor the timeline of the server. If a promotion or timeline change occurs during the backup, the data will be uploaded but not finalized, and WAL-G will exit with an error. The logs will contain the necessary information to finalize the backup, which can then be used if you clearly understand the risks."

### MySQL

Percona recommends replica backups and ships two options for them. The [replication environments page](https://docs.percona.com/percona-xtrabackup/8.4/make-backup-in-replication-env.html) states that `--slave-info` "prints the binary log position and name of the source server" and "writes this information to the `xtrabackup_slave_info` file as a `CHANGE REPLICATION SOURCE TO` statement", which is what makes the backup usable for building another replica. `--safe-slave-backup` stops the replication SQL thread and "waits to start backing up until `Replica_open_temp_tables` in `SHOW STATUS` is zero", cycling the thread until none are open, failing after a timeout that defaults to 300 seconds, and restarting the thread when the backup finishes. The recommendation is unqualified: "Using this option is always recommended when taking backups from a replica server."

So a MySQL backup taken on a replica guarantees a position in the source's binary log, and the cost is that replication apply stops for the duration.

### MongoDB

MongoDB's manual tells the operator to use a secondary, and a specific one. The [filesystem snapshot tutorial](https://www.mongodb.com/docs/manual/tutorial/backup-with-filesystem-snapshots/) states that "If you have a replica set configuration, then for your backup use a secondary which is not receiving reads (i.e. hidden member)."

Ops Manager chooses the node itself. Its [backup process page](https://www.mongodb.com/docs/ops-manager/current/core/backup-overview/) states that the cluster "determines an optimal available node to take the snapshot", and that "In most cases, the mongod determines lowest priority secondary member as the preferred snapshot node." The primary is still involved, because "Oplog tailing of the primary node is required for backups."

Percona Backup for MongoDB encodes the same preference as numbers. Its [node priority page](https://docs.percona.com/percona-backup-mongodb/usage/backup-priority.html) states that "By default, the pbm-agent to do a backup is elected randomly among secondary nodes in a replica set", that "If no secondary node responds in a defined period, then the pbm-agent on the primary node is elected to do a backup", and that the defaults are "hidden nodes - priority 2.0, secondary nodes - priority 1.0, primary node - priority 0.5". Taking manual control switches the default off: "As soon as you adjust node priorities in the configuration file, it is assumed that you take manual control over them. The default rule to prefer secondary nodes over primary stops working."

### SQL Server

SQL Server states the motive for secondary backups directly. The [backup on secondary replicas page](https://learn.microsoft.com/en-us/sql/database-engine/availability-groups/windows/active-secondaries-backup-on-secondary-replicas-always-on-availability-groups) states that "Backup operations can put significant strain on I/O and CPU (with backup compression). Offloading backups to a synchronized or synchronizing secondary replica allows you to use the resources on server instance that hosts the primary replica for your tier-1 workloads."

SQL Server documents more restrictions than any other vendor here. A full backup on a secondary must be copy-only, "since copy-only backups don't impact the log chain or clear the differential bitmap". "Differential backups aren't supported on secondary replicas." The secondary "must be able to communicate with the primary replica, and must be SYNCHRONIZED or SYNCHRONIZING". Concurrent backups across replicas are unsupported. Log backups keep working normally, and Microsoft states the guarantee for them plainly: "A consistent log chain is ensured across log backups taken on any of the replicas (primary or secondary), irrespective of their availability mode."

There is also a documented failure mode where a secondary backup harms the primary's workload. If the primary truncates its log to an LSN inside the range the secondary is backing up, error 9019 appears, and "synchronization fails for that secondary replica until the copy-only backup completes, and, if the secondary replica is set to synchronous commit, write workloads on the primary replica might be blocked until the log can harden on the secondary replica." The remedy Microsoft gives is to move that backup back to the primary. From SQL Server 2025 the restrictions loosen, since "in addition to existing copy-only and transaction log backups, you can also perform full, and differential backups on any secondary replica."

### What happens to a schedule when the primary changes

SQL Server is the only system in this set with a designed answer, and the design puts the schedule everywhere and the decision in a function. The availability group has an `AUTOMATED_BACKUP_PREFERENCE` setting whose values are documented on the [configuration page](https://learn.microsoft.com/en-us/sql/database-engine/availability-groups/windows/configure-backup-on-availability-replicas-sql-server): prefer secondary, secondary only, primary, or any replica, with a per-replica backup priority from 0 to 100. Microsoft then states that the setting does nothing by itself: "There is no enforcement of the automated backup preference setting. The interpretation of this preference depends on the logic, if any, that you script into backup jobs for the databases in a given availability group."

The operator scripts one job per replica, each guarded by the same test, and that guard is why a failover changes nothing about the schedule: "Scripting a backup job with this logic enables you to schedule the job to run on every availability replica on the same schedule. Each of these jobs looks at the same data to determine which job should run, so only one of the scheduled job actually proceeds to the backup stage. In the event of a failover, none of the scripts or jobs needs to be modified." The test is `sys.fn_hadr_backup_is_preferred_replica`, which returns 1 on the preferred replica and 0 elsewhere. Restores are barred inside the group entirely: "RESTORE statements aren't allowed on either the primary or secondary databases of an availability group."

The other tools document promotion during a backup instead of promotion between backups. PostgreSQL fails the run outright, since "If the standby is promoted to be primary during backup, the backup fails." WAL-G uploads the data but refuses to finalise it. pgBackRest avoids the question in normal operation by determining the roles at each run and by offering `prefer`, which falls back to the primary when no standby is available. PBM's incremental chains do not survive the loss of one node at all, because the chain must continue on the node that took the base, and otherwise "you must start the incremental backup chain anew on another node."

## Consensus, disagreement, and what remains unestablished

### Question one: what a backup is once it stops being a full copy

The industry agrees on four points. A backup becomes a set of artefacts with a dependency order, and the newest artefact alone restores nothing. The vendor ships the tool that puts them back together, in every case here. That tool produces a full copy rather than a running database, so a log replay still follows. And the vendor tells the operator that tracking which artefacts are still needed is the operator's job, most explicitly in PostgreSQL's statement that it "has no built-in mechanism to figure out which backups are still needed".

They disagree on who performs the recombination. SQL Server folds it into `RESTORE` so no separate tool exists, PostgreSQL and Percona give the operator a distinct command to run at a distinct moment, Litestream folds it into `restore` as well, and Cloudflare D1 removes the concept from the user's view. The mechanics are the same everywhere, so what differs is how much of the chain each product shows its user.

### Question two: restoring from object storage

The consensus is that the backup tooling reaches object storage, while the database's own utilities often do not. PostgreSQL in core cannot go past a local filesystem, which the reference page and the source both show, so a remote workflow in PostgreSQL would have to run through a tool such as pgBackRest or WAL-G. Those two, and SQL Server's URL device, restore straight into the destination without a staging copy. Percona's xbcloud is the exception, because streaming without local disk is documented for the upload only, and the download extracts to disk, prepares in place, and then copies or moves into the data directory.

Free disk of about one database is the floor for every restore in this set, and no product avoids it. Two products avoid it by not restoring at all: Litestream's VFS serves pages on demand from object storage with a 10 MB cache by default, and Ops Manager serves a snapshot as a temporary read-only `mongod`. Both are read-only, and neither replaces a restore. SQL Server's file-snapshot backups avoid the copy in a third way, by keeping the database files in blob storage so that a restore manipulates snapshots.

### Question three: backups and replication

Every vendor here points the same way, which is to take the backup on a replica where the deployment allows it. MongoDB names a hidden secondary, Ops Manager and PBM both default to the lowest-priority secondary, Percona recommends `--safe-slave-backup` without qualification, Microsoft frames secondary backups as protecting tier-1 workloads on the primary, and pgBackRest's option exists "to reduce load on the primary cluster".

They agree as clearly that the primary stays involved. pgBackRest starts and stops the backup on the primary and copies a few files from it. Ops Manager tails the primary's oplog. PostgreSQL requires `full_page_writes` on the primary and, with `-X none`, waits on the primary's WAL switching. SQL Server requires the secondary to be connected to the primary and synchronised.

What a replica backup guarantees differs by system. pgBackRest claims byte-level equivalence with a primary backup. SQL Server claims a consistent log chain across replicas but refuses differentials on a secondary before SQL Server 2025, and requires copy-only for full backups. Percona's replica backup guarantees a recorded source binary log position, which is what allows it to seed a new replica. PostgreSQL's standby backup omits the backup history file and can fail an incremental for want of a new restartpoint.

On failover, only SQL Server publishes a designed answer, and it is to schedule identical jobs on every replica and let a function decide which one proceeds, so that "In the event of a failover, none of the scripts or jobs needs to be modified." The other vendors here document what happens to a backup that is already running when a promotion occurs, and they leave scheduling to the operator.

### Where the industry disagrees with itself

The industry disagrees on three points. The first is whether the database itself should speak to object storage. SQL Server built it into the engine as a backup device, ClickHouse takes the destination as an argument in the `BACKUP` statement as `backup-interoperability.md` records, and PostgreSQL kept object storage out of core and left it to pgBackRest and WAL-G. The second is whether recombination is a user-visible step, which SQL Server and D1 say no to and PostgreSQL, Percona, and MySQL Enterprise Backup say yes to. The third is whether incremental backups are worth their management burden at all, and PostgreSQL is the only vendor here that says so out loud: "Incremental backups typically only make sense for relatively large databases where a significant portion of the data does not change, or only changes slowly. For a small database, it's simpler to ignore the existence of incremental backups and simply take full backups, which are simpler to manage."

### What I could not establish

#### Whether WAL-G writes downloaded tarballs to disk before extracting them

The documentation states only that the operator passes "a path to a directory to extract to". The reverse-unpack and skip-redundant-tars flags suggest streaming rather than staging, and neither page says so. Reading the Go source under `internal/` would settle it, and I did not read it.

#### Whether pgBackRest uses any scratch space during a restore

The command and option references describe the destination directories and say nothing about temporary storage. Reading the restore implementation under `src/command/restore/` would settle it.

Every number in the disk arithmetic above is mine, derived from documented procedures.
