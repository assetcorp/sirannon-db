# Sirannon Coordinator-Backed Failover Specification

This document defines coordinator mode, in which a linearisable cluster coordinator owns primary authority and Sirannon promotes a safe replica when the primary fails. [03-replication.md](03-replication.md) defines the replication engine, the batches, and the first sync that coordinator mode uses.

---

## Cluster Coordinator

Coordinator mode uses a linearisable coordinator to store authority metadata and provide watches. The first production backend is etcd; an in-memory backend is allowed for tests and local development. The coordinator stores only authority metadata (controller lease, node session leases, group configuration, current primary, primary term, in-sync set, and compact progress markers) and never user rows or the replication log.

The coordinator must provide, at least: acquiring and renewing a controller lease; registering, reading, and deregistering node session leases; creating a replication group's state only where the coordinator holds none; reading, writing, and watching replication-group state; comparing and advancing the primary term atomically; adding and removing voters only while the group's voters match those that the caller read; admitting a node to the in-sync set only against a proven durability point; and raising a group's feature level only while every member's live session supports it. A node must create a group only through that create-only operation. A node that creates a group as its primary must record the start of the group's first term in its file before it creates the group's state, and it must remove that record when another node creates the group first.

A coordinator may also provide a watch over the node sessions of a cluster, which calls back with every node holding a live session on each registration and each lapse. A node holding that watch serves reads only from the nodes the watch names (see [05-server.md](05-server.md#get-dbidcluster)), and a node whose coordinator provides no such watch, or that reaches no coordinator, reads from the group's membership alone.

A coordinator may also provide a watch over the controller lease, which calls back with the lease on each change of holder and with none once no node holds it. A standby controller holding that watch bids for the lease only while the watch reports no live holder, while a standby whose coordinator provides no such watch bids once every `tickIntervalMs`.

## Replication Group and Node Identity

A replication group is the set of nodes holding copies of one database and sharing one primary authority; a process may host several groups, with no process-wide global primary. Each data-bearing node has a stable persisted identity, which it keeps when it restarts with an empty or replaced file. Session leases represent a running session and do not replace stable identity. A node that registers a session while an earlier session under its identity is still live replaces the earlier session, as a restarted process does before its previous lease expires. A backup cycle on any node of the group resolves its preferred backup node from the group's membership (see [02-core.md](02-core.md#preferred-backup-node)).

A node that starts while the group names another node primary, or names no primary, must leave the in-sync set in one coordinator write before it registers its session. A node whose file holds no completed sync must also mark itself repairing in that write. A primary must record that its file holds a completed sync when it records the start of its term, because its history is the group's. A node that starts while the group names it primary must accept no write until it keeps primary duty. It must mark itself repairing in one coordinator write when its file lacks the start of the group's current term, or when the highest sequence that it has assigned in its change log is lower than the group's durability point.

From feature level 2, such a node must also prove that it holds every write that it acknowledged, and once it keeps primary duty it must advance the term with itself as primary before it accepts a write. It keeps primary duty at once when the group's record shows that the in-sync set held no majority of the voters during the current term, or when the group has no other voter. While the in-sync set holds another voter, it keeps primary duty once one of those voters reports over its current connection an applied sequence no higher than its highest assigned sequence, and it must mark itself repairing when all of them report a higher sequence or when `coordinator.sessionTtlMs` passes without such a report. While the in-sync set holds no other voter, it keeps primary duty once `n - m + 1` of the other voters that are neither repairing nor faulted report sequences no higher than its highest assigned sequence, where `n` is the number of voters and `m` is a majority of them, or once all of those voters do when fewer remain. It must mark itself repairing when any of those voters reports a higher sequence. A repairing node rebuilds in place through a full copy under its own identity. A primary must reset a replica's acknowledged sequence whenever that replica opens a new connection.

Each node session includes the node's client address and its replication address. In coordinator mode, a node reaches each member at the replication address in that member's live session, and an implementation must refuse a configured list of peer replication addresses or map of client addresses with `TOPOLOGY_ERROR`.

## Term Fencing

Each group has a monotonically increasing `primaryTerm`. Every coordinator-mode write path and replication message carries the current term; promotion atomically increments the term, records the new primary, and removes the former primary from the in-sync set. A primary may accept writes only while it proves current authority, and must fail closed for new writes and for in-flight writes that cannot prove it when renewal fails. The coordinator must apply a primary's change to the in-sync set, the durability point, or the set's admissions only while the group names that node as primary in the term that the change carries. A primary whose change the coordinator refuses this way must fail the write that waits on the change with `STALE_PRIMARY`. Replicas reject batches, sync messages, and forwarded writes from a stale term or a non-current primary. A former primary that observes a newer term demotes, leaves the in-sync set, and reconciles its history with the new primary's as any replica does (see [History Reconciliation](#history-reconciliation)). The reconciliation undoes every write that only the former primary held, and keeps a copy of each one in `_sirannon_rolled_back_changes` so that an operator can review it. An operator can still mark a node faulted, which keeps it out of the read, write, and promotion paths until the operator remediates it. A node must record that it holds quarantined writes whenever it finds itself in the faulted set, and that includes the first group state that it reads after a restart. Once an operator clears its fault and marks it repairing, the node must rebuild through a full copy, and the copy deletes that record.

## In-Sync Set and Promotion

The in-sync set holds the primary and the voters that hold every write that the primary acknowledges, and only a node in the set serves `majority` reads or qualifies for promotion. The durability point is a sequence in the current primary's change log, and promotion resets it to 0. Before a new primary sends a batch, answers a sync request, admits a node, or acknowledges a write, it records the start of its term: it resets every replica's acknowledged sequence and raises the durability point to the newest history sequence in its own change log. From feature level 2, the primary must change the durability point only when it records the start of its term, and only the current primary admits a node to the set (see [Recovery and Rolling Upgrades](#recovery-and-rolling-upgrades) for level 1). The primary admits a node only once the node's applied sequence in that primary's log reaches both the group's recorded durability point and the highest sequence that the primary has acknowledged, and the node has reconciled its history with that primary's. From the moment that the primary requests an admission, it must wait for the node to hold every write that it acknowledges, although only the voters that the coordinator records in the set count towards the majority. The primary must also keep counting a node whose removal it requests until the coordinator records the removal. The primary must never admit a repairing or faulted node. A repairing node that finishes the sync that rejoins it must clear its repairing flag in one coordinator write that states that it finished that sync in the current term, and the coordinator must refuse to clear the flag on a node's own request that lacks that statement. A node that an operator marks repairing must rebuild through a full copy, whether it is starting or already serves its data, once it has kept the changes that the primary can lack (see [History Reconciliation](#history-reconciliation)). A node that serves its data when an operator marks it repairing must make no coordinator write that marks it repairing during that rebuild, and it must read the group's state again before it starts the full copy. When that state shows that an operator has cleared the flag, the node must cancel the rebuild and keep its rows. The primary must remove from the set a replica that reports a storage or sync error, or that has not acknowledged over its current connection a change whose sequence the primary assigned more than `coordinator.maxReplicaLagMs` earlier. The coordinator must refuse a removal that the primary requests when the in-sync voters that remain are fewer than a majority of the voters.

The group records the last term in which the in-sync set held a majority of the voters. The coordinator must set that record to the current term on every write that leaves the set with that majority, and also when it raises the feature level. An operator's write of the group's state that states no such term must set it to the term that the write records.

Automatic promotion may choose only a replica whose session lease is alive, that is in the in-sync set, that has no storage, checksum, sync, or repair error, and whose promotion the controller can record while atomically advancing the term. A promotion proceeds only while the group has no primary or its primary is the node that the controller found unfit, so that two promotion attempts that saw the same failure advance the term once. When no replica qualifies, Sirannon fails closed with `NO_SAFE_PRIMARY` and does not promote an arbitrary node. Production-safe automatic write failover requires at least three voting data-bearing nodes in a group.

## Voter Changes

The members of a group are its voters and its pending voters. When an operator adds a voter, the coordinator records the node as a pending voter and marks it repairing. A pending voter counts towards no majority, and the controller never promotes it. The coordinator moves a pending voter into the voters and the in-sync set in one write, on the request that admits it once it finishes a full copy in the current term. When an operator removes a voter or a pending voter, the coordinator removes the node from the voters and from every set that the group records for it. A group state written without a list of pending voters has no pending voters. The coordinator must refuse to create a group, or to add a voter, when the voters and the pending voters would number more than seven.

While the group has a pending voter, the coordinator must refuse every voter change except the removal of that pending voter. The coordinator must also refuse to remove the current primary, and it must refuse to remove a voter when the in-sync voters that remain are fewer than a majority of the voters that remain. Removing a pending voter changes neither count, so the coordinator never refuses it for that reason.

The primary must refuse acknowledgements, forwarded writes, and sync requests from a node outside the group's members. A node outside its group's members must refuse reads and writes with `TOPOLOGY_ERROR`. The primary must count a write against the voters in the newest group state that it holds when it acknowledges the write.

## History Reconciliation

Each node in coordinator mode records the primary term whose history it holds, whatever its `initialSync` setting, and a node that starts with `initialSync` false and no recorded term must record the current term. A primary records its own term once it has recorded the start of that term, and a replica records a term once it has reconciled its history with that term's primary, through a resumed answer or a full copy. The `txId` of a transaction identifies it in the history, and the highest HLC among its changes gives its position there.

When the group's term differs from the term that a replica records, the replica sends the current primary a `SyncRequest` whose `historyTail` names the newest history transaction in its change log, or the transaction that its last full copy ended with when that one is newer, and the replica keeps serving its data until the answer arrives. The replica sends the request again when no answer arrives within `syncAckTimeoutMs`, when the primary refuses it, or when the term changes. A node that held primary authority in the term that it records sends the request too, once the group moves to a later term. A repairing or faulted node and a node that is copying send no such request, because the repair and copy paths rejoin them, and a replica whose change log holds no history transaction asks for a full copy.

A node that holds a completed sync must keep its rows until it has kept every history change that the primary can lack, and only then start a full copy. A repairing node therefore starts with its rows in place, and before it rebuilds it sends the same request, which the primary answers as below. On a resumed answer whose shared transaction the node holds a record of, the node copies into `_sirannon_rolled_back_changes` every history change with an HLC higher than the shared point's, and marks each one as compared with the primary. On any other answer, because the primary no longer keeps the history to compare against, the node copies every history change that the current primary did not write, and marks each one as not compared. A replica that refuses a resumed answer keeps its changes the same way before it asks for a full copy. A faulted node, and a repairing node that has not finished the full copy for the current term, process no batch while they serve their data, so that no change from the primary joins the history that they keep.

The primary answers a request that carries `historyTail` only once it has recorded the start of its term. When the primary's change log holds the tail's `txId`, the shared point is that transaction; otherwise the shared point is the newest history transaction that the primary held when its term began and whose HLC is lower than the tail's. With a shared point, the primary answers with a `SyncComplete` that sets `resumed`, names the shared point in `historyPoint`, sets `snapshotSeq` to the shared transaction's highest sequence in the primary's change log, and carries no manifests, and the primary keeps its change log after that sequence from pruning until the replica reports its position or `maxSyncDurationMs` passes. Without a shared point, the primary removes the replica from the in-sync set, resets the replica's acknowledged sequence, and answers with a `SyncComplete` that leaves `resumed` false. On that answer the replica asks for a full copy, unless it cancels its rebuild as [In-Sync Set and Promotion](#in-sync-set-and-promotion) requires.

On a resumed answer the replica runs one transaction that copies into `_sirannon_rolled_back_changes` every history change with an HLC higher than the shared point's; undoes those changes, newest first and from the row images in its change log; deletes them and the column versions stamped after the shared point; keeps the change-log entries that the undo writes without a node ID or HLC, so that local subscribers and live queries receive the reverse changes while the undo replicates to no peer and joins no history; records that it has applied the primary's change log up to `snapshotSeq`; and records the answer's term. A reader sees the replica's data from before that transaction or from after it. The replica then sends `snapshotSeq` to the primary as a `ReplicationAck` with an empty `batchId`, so that the primary resends its history after that sequence. The replica refuses a resumed answer and asks for a full copy when a change to undo is a schema change or lacks the row image that the undo needs, when it holds no record of the shared transaction, or when its last full copy ended with a later transaction than the shared one.

Before the primary streams a full copy for a request that carries no `historyTail`, it removes the joiner from the in-sync set and resets the joiner's acknowledged sequence, because the copy replaces the joiner's rows. From then until it streams that joiner another full copy or loses primary authority, the primary admits the joiner to the in-sync set, and counts it toward a write concern, only on an acknowledgement whose `copyRequestId` equals that request's `requestId`. The joiner sends its acknowledgements on its `Replicate` stream and its request on its `Sync` stream, and gRPC keeps messages in order only within one stream, so an acknowledgement that the joiner sent before the copy can reach the primary after the reset. The primary may still use any acknowledgement from the joiner to choose the next batch that it sends. The joiner must also remove itself from the in-sync set before it sends a request for a full copy, so that it stays out of the set until the copy completes whatever release the primary runs. In coordinator mode the copy's `SyncComplete` names in `historyPoint` the newest history transaction that the copy holds. Once the copy is verified, the joiner copies into `_sirannon_rolled_back_changes` every history change with an HLC higher than that transaction's, marked as compared with the primary, because the copy replaced the rows that those changes wrote. In the same transaction it deletes every stamped change and every column version that predates the copy, records that transaction as the point at which its history begins, records the copy's term, and records the copy's `requestId`. Every `ReplicationAck` that the joiner sends after that transaction carries the recorded `requestId` as `copyRequestId`. A joiner that predates the field sends no `copyRequestId`. After a full copy from a primary that applies this rule, such a joiner therefore stays out of the in-sync set and counts toward no write concern until it is upgraded and completes another full copy from that primary, or until the group moves to a later term. An operator can start that copy by marking the node repairing.

A replica that gains primary authority while it reconciles stops reconciling and keeps its data, because its history then becomes the group's, unless a full copy has already replaced the rows of one of its tables.

Only a request that reconciles a replica's history carries `historyTail`. A primary that predates these fields ignores `historyTail` and streams a copy, and a replica that receives a copy batch answering its reconciling request asks for a full copy. A replica that predates these fields never sends `historyTail`, so it reconciles no history, and every sync that it requests is a full copy.

## Controller, Liveness, and Maintenance

One active controller per cluster holds the controller lease and makes failover decisions; standby controllers watch the lease and take over on loss. Coordinator lease expiry or explicit deregistration is the authoritative node-death signal; a transport disconnect is connection state that may drop a replica from the in-sync set but must not by itself trigger promotion. Coordinator mode provides maintenance primitives to drain a node, move primary duty before planned work, remove replicas from safe sets, wait for in-flight work, deregister a session, and rejoin after restart. Sirannon does not provision infrastructure; it detects registration through the coordinator, assigns work, validates catch-up, and marks a node safe only once it is current.

## Recovery and Rolling Upgrades

When Sirannon cannot prove a safe primary, it fails closed; there is no force-promotion or unsafe-recovery API. An operator restores a backup, rebuilds a node, or repairs the deployment, then rejoins through the normal sync path. Nodes register package, spec, and protocol compatibility metadata; the controller rejects an incompatible major protocol change and allows mixed minor or patch levels only while metadata formats, wire formats, and safety semantics stay compatible. New durable metadata or new safety semantics require an explicit cluster compatibility gate before activation, unless a node that predates them only loses admission to the in-sync set and credit toward write concerns, as with `copyRequestId` (see [History Reconciliation](#history-reconciliation)).

Each group records a `featureLevel`, which is 1 in a group state written without one. A node must register in its session the highest feature level that it supports, and must refuse to start when the group's level is higher. The coordinator must raise the level only on an operator's request, only while every member holds a live session that registers that level or a higher one, and must refuse to lower it. At level 1, a primary must also raise the durability point to the sequence of each `majority` write before it acknowledges the write, and a replica may ask the coordinator to admit it once its applied sequence reaches the durability point, in the same write that clears its repairing flag. From level 2, the primary changes the durability point only when it records the start of its term, and only the primary requests admissions. A node whose file records the start of a primary term but no sync at all held primary duty under a release that recorded no completed sync for a primary, so on start it must record that its file holds a completed sync and keep its rows.

## Node Health

```text
NodeHealth {
  state:    'healthy' | 'degraded' | 'failing_over' | 'repairing' | 'syncing' | 'unavailable'
  reason:   'in-sync' | 'lagging' | 'coordinator-unreachable' | 'draining' | 'repairing' | 'faulted' | 'not-member' | 'sync-pending' | 'no-group-state'
  canRead:  boolean
  canWrite: boolean
}
```

`canRead` is true when the sync phase is `ready`, the group's members include the node, and the group's draining, repairing, and faulted sets exclude the node; `canWrite` also requires current primary authority.

The first matching condition sets `state` and `reason`: a `syncing` or `catching-up` sync phase, `syncing`; no group state, `unavailable`/`no-group-state`; the group's members excluding the node, `unavailable`/`not-member`; the repairing set holding the node, `repairing`; current primary authority without `canWrite`, `failing_over`; `canRead` false, `unavailable`; a last successful coordinator call older than the node's session lease, `degraded`/`coordinator-unreachable`; the in-sync set excluding the node, `degraded`/`lagging`; no match, `healthy`/`in-sync`. `NodeHealth` covers only the reporting node, so the state of another node in the group never changes it. A `syncing`, `failing_over`, or `unavailable` reason names the excluding condition: `sync-pending`, `draining`, `faulted`, or `not-member`.

Outside coordinator mode the state is `syncing` during a `syncing` or `catching-up` sync phase, `unavailable`/`sync-pending` during a `pending` one, and `healthy`/`in-sync` during a `ready` one; `canRead` is true when the sync phase is `ready`, and `canWrite` also requires the primary role.

## Conformance Invariants

Coordinator mode conforms only when its test suite proves, with a real coordinator and real multi-node groups: at most one writable primary per group and term; no loss of a `majority`-acknowledged write when only the failed primary is lost; stale primaries reject writes, batches, forwarded transactions, and sync messages; minority partitions fail closed for writes; only in-sync replicas are promoted; clients reroute writes to the new primary or receive a clear error; a returning former primary rejoins through sync without an operator, undoes every write that only it held, and keeps a copy of each of those writes in `_sirannon_rolled_back_changes`; a node restarted while its previous session is still live rejoins under its identity; a replica that holds history which the new primary lacks discards that history and resumes from the new primary's; a replica is readmitted to the in-sync set only once it holds every write in the new primary's history up to the durability point; a copy that restarts under its identity with an empty or replaced file is never promoted and rejoins the in-sync set only after a full copy; a restarted primary keeps its duty, in a new term, only when it holds every `majority`-acknowledged write; under concurrent write load with every voter live and current, every `majority` write succeeds; the primary removes a stalled in-sync replica within `coordinator.maxReplicaLagMs` and one coordinator write; a group never holds more than seven voters; the coordinator refuses to raise the feature level while a member's session registers a lower one; removing a voter never removes the current primary or leaves fewer in-sync voters than a majority; an operator can always remove a pending voter; a primary that stops between creating its group and serving its first write keeps primary duty when it restarts; moving each copy of a group in turn under write load, the primary included, loses no `majority`-acknowledged write; of two nodes that create the same group together, only one creates its record; and health state reports write availability, read availability, coordinator status, current primary, primary term, and repair state accurately.
